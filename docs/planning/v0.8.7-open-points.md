## Latent issues noticed but not fixed

- ~~`XmlChangeLog::version()` returns `0.0.0` for `yars --version`.~~
  **Fixed 2026-05-16 in commit `28120eb`** — lifted the registrations
  into `XmlChangeLog::initialize()`, called early in
  `YarsConfiguration::init`. While there, also propagated CMake
  `PROJECT_VERSION` to C++ via `YARS_VERSION_STRING` so the output
  distinguishes binary from XML schema:
  `yars 0.8.7 (XML schema 0.8.41)`.
- **Shadow support — partly working 2026-05-19, NOT yet merged.**
  On branch `feat/linux-ci-verification` (commits `92b204a`,
  `e1ed9c9`, `1d1d894`, `12c7cd7`). Master is untouched.

  **What works:** real dynamic shadow maps render. The two-layer Ogre
  14 issue that blocked prior attempts is resolved:
  1. `SceneManager::setShadowTextureCasterMaterial(MaterialPtr)` was
     required in addition to `Technique::setShadowCasterMaterial`.
     Ogre falls back to a global default for the caster pass.
  2. A custom `YARS/TextureShadowReceiver` with GLSL programs (wired
     via `SceneManager::setShadowTextureReceiverMaterial`) is required
     because `Ogre/TextureShadowReceiver` is fixed-function and
     silently breaks the modulating pass on GL3+ core.

  Both YARS shadow materials tag their technique with
  `scheme ShaderGeneratorDefaultScheme` so the
  `SGTechniqueResolverListener` doesn't lazily replace them.

  **What doesn't work yet:** shadow placement is offset from
  casters. The receiver shader uses
  `texture_viewproj_matrix * vertex_object_space`, which projects
  each renderable's local coordinates as if they were world
  positions — so the ground (at world origin) sees shadows
  correctly, but walls/robot (at non-origin world positions) cast
  shadows displaced toward the world origin in the shadow texture.

  Attempted fixes:
  - `texture_worldviewproj_matrix` (or explicit
    `world_matrix * texture_viewproj_matrix * vertex`) → shadows
    DISAPPEAR. UV debug visualisation confirms UVs *do* vary
    spatially across [0,1], so the projection reaches the shadow
    texture; it just samples WHERE THE CASTER DIDN'T WRITE.
  - Y-flip after `world_matrix * texture_viewproj_matrix * vertex`
    (because `Matrix4::CLIPSPACE2DTOIMAGESPACE` has `-0.5` in Y but
    the GL FBO render of the caster pass doesn't flip) → produced a
    single small shadow blob in a different wrong corner.

  Hypothesis: there's a coordinate-axis convention mismatch (likely
  both Y *and* X, possibly Z-up/Y-up related) between Ogre's
  `texture_viewproj_matrix` and how the GL3+ render system writes
  the shadow texture, on top of the world-matrix question. The right
  way to nail this is to **read Ogre's RTSS-generated shadow receiver
  shader source** as the reference — it bakes the same projection
  Ogre expects, and the exact transform will be visible there.

  All v4+ plumbing (caster + receiver materials, MaterialManager
  wiring, scene-level setup) stays on the branch. Placement fix
  picks up from there.

  Investigation history (kept for archaeology):

- **Earlier shadow attempts — v3/v4 investigations 2026-05-18/19.**
  v4 added a hand-rolled GLSL caster (`YARS/TextureShadowCaster` in
  `materials/YARSShadowCaster.material`, commit `de31795`) plus
  `Technique::setShadowCasterMaterial` wiring in `MaterialManager`
  (commits `0d3d735` / `9731bd5`). Those landed cleanly and are inert
  with `SHADOWTYPE_NONE`. The actual enable attempt revealed two
  layered Ogre 14 issues:
  1. `Technique::setShadowCasterMaterial` per-technique is **not
     enough** — Ogre uses a global default for the caster pass
     (`Ogre/TextureShadowCaster`, fixed-function, fails on GL3+
     core: "technique has no Vertex Shader"). Fix: also call
     `SceneManager::setShadowTextureCasterMaterial(MaterialPtr)`.
     Verified this swap works.
  2. After (1), the error changes from `Ogre/TextureShadowCaster has
     no Vertex Shader` to `Chain/Wheel has no Vertex Shader` (a
     regular YARS material). So during shadow rendering, Ogre is
     selecting each YARS material's **base technique** (scheme `""`,
     no GPU programs) instead of its RTSS-generated technique
     (scheme `"ShaderGeneratorDefaultScheme"`). The exception is
     caught-and-swallowed by `OgreHandler::step` each frame, breaking
     the render chain mid-frame. Visually: dark-blue cleared
     buffer with sawtooth border and one tiny robot blob — the
     same v3 failure pattern, just for a different root reason.
  Stock `Ogre/ShadowBlend*.vert/frag` shaders also fail to compile
  (`OGRE_UNIFORMS syntax error` because the GLSL preprocessor isn't
  expanding `#include <OgreUnifiedShader.h>`), but those errors are
  present in the working baseline too — not what's blocking us.

  Path forward (next attempt; not pursuing now):
  - Either: write actual `.material` files with explicit GLSL programs
    for every YARS material so the base technique has working shaders
    regardless of which technique Ogre picks during shadow rendering.
    Big change touching all of `MaterialManager` + ~10 new shader files.
  - Or: debug Ogre 14's active-scheme handling during shadow render —
    figure out why `Material::getBestTechnique` returns the no-shader
    base technique instead of the RTSS technique when shadows are on.
    Possibly subclass `SGTechniqueResolverListener` to intercept the
    scheme query during the shadow pass.
  - Or: write `YARS/TextureShadowReceiver` with hand-rolled GLSL
    (mirror of v4's caster work) and wire it via
    `SceneManager::setShadowTextureReceiverMaterial`. Untested whether
    this bypasses the technique-selection issue.

  All v4 plumbing (caster .material + GLSL + MaterialManager wiring)
  stays in tree as scaffolding for the next attempt; it's harmless
  with shadows off.
- `OgreHandler` is still a singleton, and **stays that way**:
  pre-flight in openspec change `refactor-ogrehandler-singleton`
  (2026-05-18) found Ogre 14's `Singleton<Root>` base class
  asserts on a second instance
  (`OgreAssert(!msSingleton, "There can be only one singleton")`
  in `OgreSingleton.h:93`). Multi-Root is framework-blocked.
  A cosmetic YARS-side cleanup is still possible (drop the
  `instance()` accessor, hand ownership to `YarsViewModel` via
  `unique_ptr`) but deferred — it rearranges deck chairs around
  an immovable Ogre constraint and has no concrete driver.
- `_groundShape` in `Environment` is still a raw `btCollisionShape*`.
  Bullet has its own ownership protocol so this isn't urgent; consider
  `unique_ptr<btCollisionShape>` once we audit Bullet's deletion rules.

## CI / packaging state

**Updated 2026-05-16** — Linux + macOS CI are both green on the
post-modernization tree (Linux run `25967849242`, macOS run
`25967849230`). The earlier "disabled" claim was wrong: CI had been
re-enabled in commit `8cf76d8` after the Linux port verification, but
every push from v0.8.6 onwards was silently red because the runners
still installed `libboost-program-options-dev` / `catch2` instead of
`libcli11-dev` / `cli11`. Fixed in `ff451c8`.

Still-warning items, non-fatal:

- ~~CSV regression check is informational~~ **Done 2026-05-18 in
  openspec change `enforce-csv-reference-regression`.** Per-platform
  references (`xml/reference_logfile.linux-x86_64.csv` and
  `xml/reference_logfile.macos-arm64.csv`), both CI-generated, both
  sized to the 2 000-iter audit budget. Both runners' diffs are
  now bit-exact and fatal; the warning fallback is gone.
- ~~FFmpeg video capture missing .mp4~~ **Done 2026-05-18 in openspec
  change `fix-ffmpeg-mp4-capture`.** Capture had been silently broken
  for weeks behind a `::warning::`. Seven layered fixes (cwd-relative
  plugins.cfg, missing `--capture` flag, `YARS_USE_CAPTURE_VIDEO=OFF`
  default, missing avfilter/avdevice/avutil apt deps, FFmpeg 4 vs 5
  ABI break on `AVOutputFormat` constness, default
  `captureDirectory=video`/`captureName=yars.mp4`, segment-indexed
  `-NNNN` filename suffix). CI now uploads a 600×600 H.264 mp4 +
  ffprobe summary per run, and any future regression fails the step
  loudly rather than emitting a silent warning.
- ~~Node.js 20 deprecation~~ **Fixed 2026-05-16 in commit `d484389`** —
  bumped `actions/checkout` v4→v6, `actions/cache` v4→v5,
  `actions/upload-artifact` v4→v7. All three now ship Node 24.
  Warning is gone.
- ~~`freeimage` brew deprecation~~ **Done 2026-05-18 in commit
  `e2ec4ae`** (openspec change `migrate-freeimage-to-stbi`). Dropped
  libfreeimage from both runners + Ogre's FreeImage codec. Ogre's
  STBI plugin already covers all texture formats we use (audit
  found only `.png` and `.jpg` in `materials/`). Both CIs green
  on the post-migration tree.
