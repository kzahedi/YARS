## Latent issues noticed but not fixed

- ~~`XmlChangeLog::version()` returns `0.0.0` for `yars --version`.~~
  **Fixed 2026-05-16 in commit `28120eb`** — lifted the registrations
  into `XmlChangeLog::initialize()`, called early in
  `YarsConfiguration::init`. While there, also propagated CMake
  `PROJECT_VERSION` to C++ via `YARS_VERSION_STRING` so the output
  distinguishes binary from XML schema:
  `yars 0.8.7 (XML schema 0.8.41)`.
- **Shadow support — COMPLETE (v6.1, 2026-06-11).** The full history
  below is archaeology; the placement bug was solved in v6 (2026-05-22)
  and the pipeline completed in v6.1. Current architecture and tuning
  knobs: `docs/planning/shadows_state.md`. Acceptance criteria (all six
  met): `docs/planning/shadow_goal.md`. PR to `main`: #11.

  Short version of the fix: `SHADOWTYPE_TEXTURE_MODULATIVE` + custom
  GLSL caster/receiver, with `ShadowMapper` (an `Ogre::ShadowTextureListener`)
  pushing the shadow camera's `proj × view` into the receiver material
  from C++ each frame — bypassing Ogre 14's broken
  `texture_worldviewproj_matrix` auto-param on macOS arm64 GL3+ core,
  which was the root cause of the displaced-shadow bug documented in the
  archaeology below. v6.1 added a world-anchored fixed shadow camera,
  `PF_FLOAT32_R` depth, and 3×3 PCF.

  <details><summary>Archaeology: the placement-bug investigation (v3–v5, 2026-05-18/19)</summary>

  **What worked by v5:** real dynamic shadow maps rendered. Two-layer
  Ogre 14 issue resolved: (1)
  `SceneManager::setShadowTextureCasterMaterial(MaterialPtr)` required
  in addition to `Technique::setShadowCasterMaterial`; (2) a custom
  GLSL receiver wired via `setShadowTextureReceiverMaterial` (the
  fixed-function `Ogre/TextureShadowReceiver` breaks the modulating
  pass on GL3+ core). Both materials tag their technique with
  `scheme ShaderGeneratorDefaultScheme`.

  **What was broken:** shadow placement offset from casters. The
  receiver shader's `texture_viewproj_matrix * vertex_object_space`
  projected local coords as world positions. `texture_worldviewproj_matrix`
  and explicit `world * tex_viewproj * vertex` made shadows vanish
  (sampled where the caster didn't write); Y-flip variants produced a
  blob in the wrong corner. Resolved in v6 by pushing the matrix from
  C++ via `ShadowMapper` instead of relying on the auto-param.

  </details>

## CI / packaging state

**Updated 2026-05-16** — Linux + macOS CI are both green on the
post-modernization tree (Linux run `25967849242`, macOS run
`25967849230`). The earlier "disabled" claim was wrong: CI had been
re-enabled in commit `8cf76d8` after the Linux port verification, but
every push from v0.8.6 onwards was silently red because the runners
still installed `libboost-program-options-dev` / `catch2` instead of
`libcli11-dev` / `cli11`. Fixed in `ff451c8`.

**BLOCKER (2026-06-26) — shadows v6.1 branch fails CI at checkout.**
PR #11 (`feat/shadows-v6.1`) cannot pass CI: commit `8641543` bumps the
`ext/ogre-source` submodule to `e99519a` ("YARS patch: guard
`ManualObject::getShadowVolumeRenderableList` against detached node" —
one commit on top of upstream `v14.5.2-79`/`922f5b6`), but `.gitmodules`
points the submodule at upstream `https://github.com/OGRECave/ogre.git`,
where `e99519a` does not exist. CI's `Checkout (with submodules)` step
dies with `Fetched in submodule path 'ext/ogre-source', but it did not
contain e99519a…`. The patched commit lives ONLY in the local clone and
must be hosted on a fetchable remote before CI can build the branch.
Resolution pending a hosting decision (fork + repoint `.gitmodules`, vs.
apply-patch-at-build, vs. upstream PR).
